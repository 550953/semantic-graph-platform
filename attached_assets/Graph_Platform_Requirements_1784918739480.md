# Graph Platform — свод новых требований из переписки с ChatGPT

Источник: 16 shared-ссылок ChatGPT, присланных коллегой 2026-07-20. Обсуждение касается не GreenMarket, а отдельного проекта коллеги — **Graph Platform / Bank Knowledge Platform** (универсальный графовый движок знаний, изначально для банковской отчётности, с прицелом на переиспользование в т.ч. в GreenMarket через `platform_core`).

Статус: фрилансер коллеги уже начал реализацию и показал первый результат.

## 1. Стратегия внедрения

### 1.1 Инкрементальная валидация на собственной экосистеме
Не обкатывать технологию сразу на банковском (промышленном) проекте, а сначала построить и проверить граф на внутренних проектах — GreenMarket, Taxi, Platform Core, FSM Engine, Voice, Map. Этапы: (1) построить граф на внутренних проектах → (2) отработать автонаполнение графа из источников → (3) интегрировать ИИ поверх графа → (4) проверить масштабируемость на нескольких проектах → (5) перенести проверенное решение в банк.
[Источник](https://chatgpt.com/s/t_6a5b2b37f0848191aeaec022d0c33a60)

### 1.2 Self-hosting графа
Платформа с первого дня разработки ведёт граф знаний о самой себе: каждое архитектурное решение, изменение модели, новый компонент или документ автоматически становится узлом собственного графа. Система — первый пользователь своей же технологии.
[Источник](https://chatgpt.com/s/t_6a5b2b5435908191b6339cceae0eff2a)

## 2. Модель графа — новые слои и сущности

### 2.1 Project Knowledge Layer
Граф должен обслуживать не только аналитика/LLM, но и руководителя проекта: что изменилось, кто работает, на каком этапе, какие документы/формы/SQL/сервисы/тесты затронуты, что сделано. Сущность **Изменение** получает связи: форма, показатель, SQL, тесты, документация, исполнитель, срок, статус, риск. Граф — это набор проекций одной модели: аналитик видит предметную область, разработчик — техническую реализацию, LLM — объединённую семантику, PM — состояние проекта и критический путь.
[Источник](https://chatgpt.com/s/t_6a5b2beff1a48191930f4d18d7f326c2)

### 2.2 Transformation Graph (ресурсно-финансовый слой)
Изменение несёт метрики: сколько документов/SQL/сервисов затронуто, сколько человеко-часов и специалистов требуется, бюджет, срок, критический путь, риски. Модель распадается на 4 согласованных графа с общими сущностями/ID:
- **Knowledge Graph** — предметная область;
- **Implementation Graph** — документы, код, SQL, тесты, сервисы;
- **Project Graph** — задачи, исполнители, зависимости, сроки;
- **Resource Graph** — люди, компетенции, загрузка, бюджеты.

Платформа фактически становится цифровым двойником процесса развития отчётности, а не просто хранилищем документации.
[Источник](https://chatgpt.com/s/t_6a5b2c42c46481919227c67e6579edc6)

### 2.3 Review как объект графа первого класса
Рецензия отвязывается от документа — её предмет: артефакт проекта. У Review появляется собственный **Scope**: Project → Epic → Feature → Artifact → Version → Fragment, плюс автор, исполнитель, статус, история. Это позволяет одним и тем же документом пользоваться в нескольких инициативах без смешивания замечаний, а HTML-вьюер становится универсальным интерфейсом переключения между контекстами рецензирования.
[Источник](https://chatgpt.com/s/t_6a5b2d65ef6c8191a47e8efb9448da06)

### 2.4 Execution Graph (спринты и трубы)
Добавляется слой исполнения: Portfolio → Program → Project → Pipe → Release. Разделены два независимых измерения:
- **Sprint** — временной контейнер выполнения работ;
- **Pipe** ("труба") — поток изменения через стадии анализ → проектирование → разработка → тестирование → внедрение.

Одна труба может проходить через несколько спринтов, один спринт — содержать задачи из нескольких труб (связь many-to-many).
[Источник](https://chatgpt.com/s/t_6a5b2eb7aa908191aeab865217b07c06)

### 2.5 Work Item → Issue
Task и Defect — разные классы объектов (разный жизненный цикл, разные метрики управления), с общим предком **Work Item**. Дальше вводится обобщающая сущность **Issue**, объединяющая Task, Defect, Review Comment, Risk, Technical Debt, Change Request, Improvement — единая цепочка трассируемости (рецензия → дефект → задача → изменение документации → обновление графа). Отдельно вводится понятие "дефект знаний": отсутствующая сущность/связь, устаревшая документация, разрыв трассируемости, отсутствие владельца, рассинхронизация источников.
[Источник](https://chatgpt.com/s/t_6a5b2f469ba88191bcd558df4dc7a799)

### 2.6 Сводное письмо коллеге (п. 1–7)
Итоговая консолидация вышеперечисленного плюс явное решение по трубе:
- Труба **намеренно не формализуется** в онтологии на этом этапе: критерии прохождения ещё не устоялись, не все Issue проходят через трубу. Достаточно предусмотреть саму возможность связи Issue↔процесс исполнения, оставив правила использования на уровень конфигурации, а не жёсткой модели.
[Источник](https://chatgpt.com/s/t_6a5b31d39ec881919c0a8effc2bafaf5)

## 3. Роли и участники

### 3.1 Заказчик ≠ Owner
Роль **Заказчик** (бизнес-владелец/инициатор) явно отделяется от **Owner** (технический/процессный владелец конкретного объекта графа) — это разные роли, которые могут не совпадать. Роль привязывается не к персоне глобально, а к конкретной связи Person↔Object (Issue, проект, артефакт), т.к. один человек одновременно исполняет разные роли в разных объектах.
[Источник](https://chatgpt.com/s/t_6a5b32bfadf08191b4273a45a54ed551)

### 3.2 Interest Scope — вычисляемая область интересов
Область интересов персоны/роли не хранится как атрибут, а **вычисляется** из графа: прямые связи персоны (проекты, Issue, рецензии, спринты, домены ответственности) + объекты, достижимые по разрешённым типам связей. Автоматически расширяется/сужается при изменении ролей и назначений без ручной перенастройки. Становится движком персонализированного контекста — для UI, уведомлений, поиска и сборки контекста для LLM.
[Источник](https://chatgpt.com/s/t_6a5b334ba88c8191a7082a14c92081d8)

### 3.3 Actor вместо Person
Базовая сущность обобщается: **Actor** = Human | AI Agent | Service | External System. Любой Actor может владеть/исполнять/рецензировать Issue (с учётом политик доступа). AI-агент — равноправный участник графа со своим Interest Scope (что отслеживать/анализировать вместо "с чем работать"). Это защищает онтологию от переделки при появлении новых типов участников — достаточно добавить подтип Actor.
[Источник](https://chatgpt.com/s/t_6a5b346150848191a9867c090203b75f)

## 4. Продуктизация и онтология

### 4.1 Default First, Configure Second, Extend Third
Новый проект стартует не с нуля, а с дефолтного профиля: базовая онтология, стандартные роли, типовые процессы, типы Issue, шаблоны артефактов, правила вычисления Interest Scope, базовые AI-агенты, типовые запросы/представления. Дальше — итеративная доменная настройка. Принцип: изменения должны быть **аддитивными** (добавление сущностей/связей/правил), а не требовать переписывания базовой онтологии.
[Источник](https://chatgpt.com/s/t_6a5b35e95f308191b8d363f528430f09)

## 5. Архитектура платформы

### 5.1 Разбивка на движки
Платформа состоит из независимых модулей-движков:
- **Graph Engine** — хранение графа, узлы, связи, представления;
- **FSM Engine** — жизненные циклы объектов и допустимые переходы;
- **Review Engine** — рецензирование, согласование, голосование;
- **Ontology Engine** — типы узлов/связей, правила предметной области;
- **RAG Engine** — привязка документов к графу, интеллектуальный поиск;
- **Visualization Engine** — React Flow, представления, фильтры, раскладки.

FSM Engine явно не банковская специфика — он универсален (заказ, документ, задача, договор, заявка, инцидент, PR, любой бизнес-процесс) и должен стать первым независимым модулем платформы.
[Источник](https://chatgpt.com/s/t_6a5cb3b64ca8819187e7277f5ef68f4f)

### 5.2 PI (Platform Interactive) как отдельный архитектурный слой
React Flow — только визуальный canvas-компонент (отрисовка/перемещение/масштабирование узлов), уровень UI. **PI (Platform Interactive)** — более высокий слой: панели, карточки объектов, режимы просмотра, контекстные действия, инспекторы, поиск, фильтрация, сценарии взаимодействия, интеграция с Review/FSM/RAG. Замена React Flow на другую библиотеку не должна требовать изменения PI (аналогия: Monaco Editor внутри VS Code).
[Источник](https://chatgpt.com/s/t_6a5cb45a937c8191bae3c1874e753dfa)

### 5.3 Graph Copilot
Полноценная архитектура чата с графом, а не просто "чат поверх графа":
```
React UI → Chat Panel → LLM Gateway → {Graph API, Prompt Builder} → LLM Provider
```
Каждый вопрос — объект графа **Question** (автор, время, роль, проект, открытая диаграмма, выбранные узлы, prompt, модель, ответ, стоимость, токены, latency, feedback) — база для аналитики (популярные/дорогие вопросы, где не хватает связей в графе, неудачные ответы, стоимость сопровождения домена). Вводится сущность **Conversation** (Question/Answer/Reasoning/Decision) — повторяющиеся вопросы система предлагает превратить в постоянный объект графа.

Ключевой отдельный компонент — **Graph Context Builder**, промежуточный слой между графом и LLM: по контексту пользователя (роль, выбор, Issue, Interest Scope) собирает минимально необходимый подграф перед Prompt Builder — снижает расход токенов и повышает качество ответов. LLM не должна работать с графом напрямую.
[Источник](https://chatgpt.com/s/t_6a5cc37331b081918e5f8fc39cd4899e)

## 6. Масштаб организации

### 6.1 Workspace-иерархия
Вводится сущность **Workspace** (фрилансер, студия, подразделение, компания, холдинг) с иерархией:
```
Workspace → Portfolio (группа проектов) → Project → Graph
```
Внутри Workspace общие сущности между проектами: Actor'ы, AI-агенты, шаблоны, процессы, компоненты, библиотеки, знания, решения, архитектурные паттерны — платформа может предлагать переиспользование компонента, реализованного в одном проекте, в другом. Архитектура масштабируется без изменений от одного разработчика до международной корпорации — меняется только объём данных. Рекомендовано закладывать это направление рано (сразу после функционального паритета с React Flow), а не откладывать.
[Источник](https://chatgpt.com/s/t_6a5d09c54d9c819183fb51bca1e11774)
